# ADR 系統 — 四站架構決策紀錄

本目錄是 xingai.app / invest.xingai.app / travel.xingai.app / cook.xingai.app 四個網站的 **Architecture Decision Record（ADR）** 存放處：任何網站改動——新頁面、新功能、架構決策、上線、撤除——都要在這裡留一筆。

## 為什麼要有這個系統（2026-10-16 星哥定）

改 code 只是結果；**為什麼改、誰拍的板、當時是什麼狀態**，時間一長就會忘。ADR 就是給未來的工程師（和未來的小甜甜）看的決策帳本：哪天想推翻一個做法，先來這裡看當初為什麼這麼定、是第幾筆決策，再決定要不要翻。

## 寫法規則

1. **一筆 ADR = 一個決策**。一個 commit 若含兩個獨立決策，拆兩筆；一個決策跨多個 commit，寫一筆並在「關聯」欄列全部 commit。
2. **編號全域連續、不重用**：四個站共用同一條編號序列（ADR-0001、ADR-0002……）。編號一旦發出，永不改派給別的決策。
3. **舊筆永不刪除**：決策被推翻時，不刪舊 ADR、不改舊 ADR 的決策內容——新增一筆 ADR 說明推翻/撤除，把新筆狀態標為 `Superseded`（被新決策取代）或 `Reverted`（撤除、回到改動前），並把舊筆的「狀態」欄改為 `Superseded`，兩筆在「關聯」欄互引編號。
4. **狀態詞彙固定**：
   - `Accepted` — 已拍板並生效（或已上線）。
   - `Testing` — 測試/試行階段，尚未定版。
   - `Superseded` — 本筆決策已被另一筆 ADR 取代（須註明被哪一筆取代）。
   - `Reverted` — 本筆記錄的是一個撤除動作（把先前某筆決策的落地成果撤掉）；被撤的那筆同步標 `Superseded`。
5. **每筆必填欄位**（照 template.md）：編號 / 日期 / 網站 / 標題 / 狀態 / 背景與原因 / 決策內容 / 誰拍板 / 影響與後果 / 關聯。查不到的欄位寫「未記錄」，不許編造。
6. **「誰拍板」要寫清授權來源**：星哥親口定的寫「星哥拍板」並盡量附原話或時間點；小甜甜拍板的，必須寫明授權來源（例如「星哥 2026-10-16 授權『你來訂吧』後小甜甜拍板」）。沒有授權來源的自行決定不許寫成已拍板。
7. **沒有 ADR 的網站改動不算辦完**：上線/撤除的同一個工作回合內補齊 ADR 並更新 INDEX.md。
8. **新架構決策先對照既有 ADR**：特別是 ADR-0016（四站 cache 架構約定）——與它衝突的新做法，必須先有一筆新 ADR 說明為何破例，並把舊筆標 Superseded，不許默默繞過。

## 檔案命名

`ADR-XXXX-<slug>.md`，slug 用英文小寫連字號，簡述決策主題（例：`ADR-0001-invest-etf-curation-page.md`）。

## 索引

`INDEX.md` 是總索引：全域表格＋每站分節。新筆寫完必須同步更新索引，索引與檔案對不上以檔案為準並立即修索引。

## 發布到網站（2026-10-16，ADR-0017）

本目錄同時發布在主站 **https://xingai.app/adr**（總索引）與 **https://xingai.app/adr/<slug>**（每筆一頁，slug＝檔名去掉 `.md` 後轉小寫）。該頁面是內部文件櫃：不進主站導航/頁腳/sitemap，全頁 `noindex, nofollow`，只有知道網址的人能讀。

發布步驟（新增或修改 ADR 後必做，否則網站版會落後）：

1. 把本目錄的 md 檔（新筆 ADR 檔＋更新後的 `INDEX.md`；`README.md`、`template.md` 有改也一併）同步覆蓋到 repo `xingaiapp/xingai-dot-app` 的 `content/adr/` 目錄——該目錄是網站的發布源，內容須與本目錄逐字一致。
2. 連同其他改動比照既有流程推上 repo 的 main（Git Data API），Vercel 自動部署後即生效。
3. 上線後抽查：/adr 索引表格含新筆、/adr/<新筆 slug> 打得開、內容與源文件一致。
